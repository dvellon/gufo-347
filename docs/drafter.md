Speculative decoding is only as fast as its draft head is accurate *on your traffic*. The public MTP head that ships
with the model is general-purpose. We fine-tuned it on our own traffic: the target model's answers to our own code,
prose and agent prompts. That gave the speed-ups below at **identical output**, because the strict tier verifies every
drafted token. We do not publish our head, because it was trained on private data. This page and the tooling in
[`drafter-training/`](https://github.com/dvellon/gufo-347/tree/main/drafter-training) show you how to train one on yours.

## What to expect, by workload

From benchmark run 287. The comparison is private drafter (C) vs public drafter (B), same binary, strict tier:

| workload | gain (C / B, 95 % CI) | acceptance B -> C | tokens per target pass B -> C |
|---|---|---|---|
| canonical prose | n/a  | 0.401 -> n/a | 2.12 -> n/a |
| chat with thinking | n/a  | 0.649 -> n/a | 2.81 -> n/a |
| coding agent, 1 session | n/a  | 0.776 -> n/a | 4.35 -> n/a |
| coding agent, 8 sessions | n/a  | 0.875 -> n/a | 3.11 -> n/a |

How to read it:

- **Prose and chat gain the most.** These are the token streams where the public head is weakest. Agent tool traffic
  is already highly predictable (acceptance ~0.76-0.84 with the public head), so there is less to gain there.
- **At 8 sessions the gain is close to zero.** The batch is limited by verify and prefill cost, not by draft accuracy.
- **C is not a pure head effect.** It also uses a smaller re-quantised copy of the head (about +0.6-0.8 % from kernel
  speed alone) and a draft-vocabulary table built from our own token counts. The head's own share is somewhat
  smaller than the C / B column.
- **Earlier internal measurements agree.** Against the stock head, our first fine-tuned head gave +5.5 % canonical
  decode, and the final one gave +10.8 % canonical decode but only about +1 % on agent traffic.

**Rule of thumb:** expect roughly +5-11 % on prose and chat that look like your training prompts, and +1-3 % on agent
tool traffic. Expect less on traffic that does not look like your training data.

## Data: what worked

| source | amount | used for | did it help? |
|---|---|---|---|
| **on-policy answers**: your prompts, answered by the *target model itself* (greedy) | 300 prompts (100 code, 100 prose, 100 agent next-step), ~0.43 M prompt tokens, ~0.14 M generated tokens per answer set; ~1.58 M thinking + ~0.09 M no-think tokens in the final training mix | stage 2 (the lever) | **yes**: the main gain |
| teacher-forced corpus (your own code, docs, patches, build logs) | 16.9 M tokens built; ~3.3 M captured and used | stage 1, then replayed at x0.3 in stage 2 | first head only; more of it plateaued |
| coding-agent transcripts | 444 M tokens available | agent prompts; token counts for the vocabulary table | a dedicated agent-tool continuation was KILLED live |
| held-out evaluation | 100 records (60 thinking: code / prose / agent; 40 no-think), split by prompt key, 32-gram leakage check | selection and judging | essential: see pitfalls |

**Why on-policy.** The draft head has to predict what *this* model will say next, not what a human wrote. A
teacher-forced corpus taught the head a lot offline, but the gain did not carry over to live serving. The target
model's own greedy answers did carry over.

**Capture format.** Each position stores the trunk's final hidden state (BF16), the token id, and the target's top-32
token ids with log-probs, plus entropy and the rank of the true next token. That is about **20.7 KB per token**
(about 20.7 GB per million tokens), so plan the disk before you start.

## Steps

1. **Pick prompts** from your own traffic, split by source key into train and held-out sets
   (`onpolicy/make_train_prompts.py`, `onpolicy/make_train_jobs.py`).
2. **Generate on-policy answers** with the target model, greedy, thinking on and off as you serve it. Then
   **capture** them with the engine's capture overlay, so the labels are the serving engine's own tokens
   (`capture/`). Answers generated by a different engine are fine as text: about 4 % of positions disagreed with our
   engine's argmax, and re-capturing fixed the labels.
3. **Build the training and evaluation sets** and check for leakage. Drop eval records that overlap training by
   >= 5 % on 32-grams, or that share a source key (`eval/s2_sets.py`, `eval/overlap_check.py`).
4. **Stage 1:** a teacher-forced fine-tune from the public head (`train/train_mtp.py`).
5. **Stage 2:** an on-policy fine-tune (on-policy data x2, corpus replay x0.3) with early stopping on the selection
   half. Then a **continuation**: 2 more epochs from the best checkpoint, with a fresh optimizer and warm-up. The
   continuation produced our best head.
6. **Export** to the same GGUF layout as the public Q8_0 head (`train/export_gguf.py`). The export uses a bit-exact
   Q8_0 quantizer, and a no-op export is byte-identical to the input head.
7. Optional: **re-quantise the routed experts** (Q4_K gate/up, Q5_1 down) with a standard GGUF requantize tool. The
   head shrank from 2.6 GiB to 1.6 GiB and acceptance did not change. Check that your engine loads those tensor
   types.
8. **Score offline**: tokens per call and depth-1 / depth-2 acceptance on the held-out judge half
   (`train/eval_offline.py`, `eval/shallow_score.py`).
9. **Test live:** an interleaved A/B where only `--mtp-model` differs. Only the live number counts.
10. Optional, our fork only: build a **draft-vocabulary table** from your token counts
    (`tools/corpus_counts_public.py`, then `tools/perm_public.py`). It is a CPU job of a few minutes.

## Recipe that worked

- **Loss:** KL divergence to the target's top-32 distribution (plus a residual bucket), + 0.5 x cross-entropy on the
  target's argmax. Depth weights decay by 0.85 per draft step, and the chain is teacher-fed for 7 draft steps.
- **Trainable parameters:**
  - a full fine-tune of the dense part (~91 M parameters);
  - LoRA on the routed experts (rank 8 in stage 1, rank 16 in stage 2);
  - the embedding and output matrices stay frozen.
- **Stage 2 settings:** lr 1.5e-5 (LoRA 1e-4), warm-up 10 steps, min-lr 0.1, grad-accum 8, 2 epochs, depth 7.
  Response tokens are weighted x2 and prompt tokens x0.5, and long records are windowed. Use a grouped MoE kernel for
  the experts, which was ~10x faster than a per-expert loop.
- **Passes:** acceptance saturated at about 4 passes over the on-policy set; 8 passes added +0.1 pp.

## Compute and cost (what we actually used)

All training ran on **one NVIDIA H100 80 GB** cloud instance at about $4.41/h:

| step | time / cost |
|---|---|
| stage 1, first head | 1.81 h, $14.01 |
| stage 2 | $3.77 |
| stage-2 continuation (the best head) | $3.29 |
| **the path that worked, total** | **about $21 of H100 time** |
| everything incl. the dead ends below (3 instances, ~35 billed hours) | $170.85 |
| optional head re-quantisation | $0 (CPU) |
| draft-vocabulary table | $0 (CPU, minutes) |
| on-policy generation + capture | local GPU, about 2 GPU-hours per 0.3 M generated tokens + ~15 min capture |

Training throughput on the H100 was about 3.1-3.7 K tokens/s with the grouped MoE kernel.

## Pitfalls

- **Cross-entropy-only fine-tuning moved the temperature, not the acceptance.** It sharpened the head's logits by
  ~1.35x and agreed with the old head on 99.995 % of drafts. Its apparent gain was only the confidence stop moving;
  at a matched stop rate it was +0.003-0.007. Judge at a matched stop rate.
- **Offline gains shrink live, by 2-5x.** Our first head was +45 % on an offline metric and +7 % live. Set your live
  expectations from that ratio.
- **Leakage inflates offline numbers.** One of our training sets shared a source key with 12-13 eval records. Split by
  prompt key and pre-register the selection / judge halves.
- **More data stopped paying.** Each doubling of the on-policy data added about +0.25 pp depth-1 acceptance, or about
  +0.1 % decode. That is roughly $50 or 13 local GPU-hours per doubling. Spend effort on matching your traffic, not
  on volume.
- **Re-quantisation can erase small updates.** Check the exported head's argmax agreement with the trained weights at
  each depth. Ours was 100 / 91 / 91 % at depths 1-3.
- **Reduction order matters in tests.** A near-tie flip failed an identity check at 8 threads but passed at 4. Pin the
  thread count for golden tests.
- **Tooling traps we hit:** CRLF line endings in shell scripts; argparse prefix matching (`--lr` matched a different
  flag, so use `allow_abbrev=False`); a process watcher that matched and killed its own session; an expanded glob that
  turned a refresh into a no-op. Also: generating and training on one GPU at once cut generation from 150 to 30 tok/s.

## What did not work (all KILLED, with the numbers)

| variant | result |
|---|---|
| cross-entropy only | temperature shift; +0.003-0.007 at a matched stop rate |
| loss on the serving vocabulary only | V -0.001 |
| two-pass depth-1 training | d1 -1.5 pp (under-trained) |
| acceptance-loss term | d1 +0.1 pp (line +0.3) |
| depth-2 LoRA, other depth / tie variants | V -0.004 .. +0.02 |
| full output head trainable | V +0.037, but -2-3 % engine cost |
| QAT + weight averaging (warm restart) | V -0.018 |
| more teacher-forced corpus | plateau |
| agent-tool continuation | +0.9 pp offline, -1.15 % canonical live |
| hidden-state taps from another layer | collapsed at lr 1e-4; +0.4 pp at 1.5e-5 |
| a different drafter architecture | d1 0.762 vs 0.803 |
| distilled smaller students | d1 -20 pp |
| a 4-bit "lean" head (Q4_K layer + Q4_0 output) | -0.23 tokens per call |
